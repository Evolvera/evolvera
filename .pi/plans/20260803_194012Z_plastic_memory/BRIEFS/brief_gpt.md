# Plan Brief — GPT — semantic-cycle plastic memory revision

## Recommendation and Goal

Regenerate the existing plan around one append-only session state machine and one compaction coordinator; do not patch the old deterministic/native-cut design. The recommended architecture is:

- edge-triggered observer→reflector work closes semantic coverage cycles at completed-turn boundaries;
- a pure fold derives cycle status, attempt suppression, and the sliding latest-four raw window;
- one detached Luna compactor prepares a verified cumulative result for the newly eligible prefix;
- one settled-only coordinator stages and applies that result through the sole `session_before_compact` owner;
- token pressure remains an emergency circuit breaker that deliberately falls through to Pi native compaction when no physically adequate staged result is ready;
- one validated project-context assembler supplies bounded summary, active-chunk index, and optional architecture index to visible runs and compactor preparation.

This is the smallest design that satisfies the revised outcome while preserving append-only evidence, native emergency behavior, legacy recall, explicit durable publication, and the visible session model. The old plan’s “no proactive compaction,” unchanged host cut, deterministic-only compaction, and three-role decisions are directly superseded (`.pi/plans/20260803_194012Z_plastic_memory/PLAN_FULL.md:37-45, 66-70`).

There is one decisive host compatibility issue the handoff’s initial delayed-boundary fixture does not settle: repeated custom 6/4 cuts cross an earlier compaction entry. Pi 0.83.0 then includes that older compaction summary inside the retained raw window. Therefore exact repeated `summary(C1–C4) + raw C5–C8` behavior is not delivered by `firstKeptEntryId=C5-start` alone. The revised plan must front-load a pure repeated-host-projection characterization and, if confirmed, add a narrowly scoped provider-context projection that suppresses superseded compaction-summary messages while retaining the latest cumulative summary and every raw entry. If that cannot be proven without hiding required native evidence, the implementation must stop; treating the first custom-cut fixture as sufficient would be unsafe.

## Verified Evidence and Assumptions

### KNOWN

- Pi copies an extension’s `summary`, `firstKeptEntryId`, and `tokensBefore` directly into both manual and automatic compaction and `appendCompaction()` does not validate the cut (`/Users/j.henrique/npm-global/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js:1363-1436, 1617-1677`; `dist/core/session-manager.js:802-816`). Missing or unsafe IDs therefore fail destructively at context reconstruction rather than at append time.
- `buildContextEntries()` emits the latest compaction first, then every ancestor from its `firstKeptEntryId` through the entry preceding that latest compaction, then later descendants (`dist/core/session-manager.js:195-225`). For the second stride, the branch is approximately `C1…C6, compact(C1–C2), C7…C8, compact(C1–C4)`. A cut at C5 consequently projects `compact(C1–C4), raw C5–C6, compact(C1–C2), raw C7–C8`. This is the required counterexample: a checkpoint that tests only the initial C1–C2 cut would omit work needed for the second stride and would later require restoration/filtering.
- Pi’s per-call `context` hook can non-destructively filter a deep copy of messages (`docs/extensions.md:648-657`; `dist/core/extensions/runner.js:744-770`). Compaction messages expose only role, summary, token count, and timestamp, not entry ID or `fromHook` (`dist/core/messages.js:48-54`). Any suppression must therefore be proven against branch order and message projection; summary-string matching alone is not safe.
- Native cut selection excludes tool results and keeps results with the assistant tool call (`dist/core/compaction/compaction.js:225-308`). A custom cycle cut does not inherit that protection automatically and should be stricter: it should begin at the context-visible start of the preserved cycle/turn, not merely at “anything except a tool result.”
- `ctx.compact()` is fire-and-forget and invokes manual `AgentSession.compact()`. That path disconnects and aborts first, resolves the current visible model’s summarization auth, labels the hook event `reason: "manual"`, and invokes native compaction if the hook returns no custom result (`dist/core/agent-session.js:1363-1436, 1908-1921`; `dist/core/extensions/types.d.ts:200-204, 440-460`). Thus an internal proactive call needs an unambiguous in-memory invocation nonce: on a stale/missing internal result the hook must return `{ cancel: true }`, never `undefined`. Real manual, threshold, and overflow events must retain intentional native fallback.
- `agent_settled` is emitted only after retry/auto-compaction/queued-continuation handling; Pi marks the run inactive before extension settled handlers (`dist/core/agent-session.js:314-321, 740-755`; `docs/extensions.md:558-571`). `isIdle()` is only `!_isAgentRunActive`, while pending-message state is separate (`dist/core/agent-session.js:587-594, 1147-1150`). Both checks plus a tracked settled epoch are required.
- The installed model records disagree on Luna’s context window: `models-store.json` says 272,000 and `config/models.json` says 300,000 (`models-store.json:1010-1040`; `config/models.json:96-115`). The resolved runtime model is therefore the only valid budget source. Both records support reasoning; installed defaults can use medium thinking without hardcoding a context size.
- Smart Compact’s reusable ordered-prefix fingerprint hashes a fixed ID prefix and permits appended suffixes (`/private/tmp/plastic-memory-evidence/pi-smart-compact/dist/index.js:1999-2039`), but its pending slot validates only TTL and session before consume (`dist/index.js:6407-6419, 6658-6677`). Its `ctx.compact()` application also uses a fixed custom instruction and clears on error (`dist/index.js:6486-6520`). Plastic-memory must adapt these ideas, not copy the weaker guard.
- Current settings still activate `npm:pi-observational-memory@3.0.3` and retain 10k/20k observational edge values (`config/settings.json:7-19`). The existing project hook caps summary/architecture at 8,000/4,000 chars and injects through `before_agent_start` (`extensions/project-memory.ts:14-19, 142-178`). These are preservation and cutover hazards, not authorization to activate the new owner.

### INFERRED

- Descendant tolerance is safe when the entire prepared branch ID vector through the preparation leaf remains an exact ancestor prefix, the captured latest-compaction identity is unchanged, and the current branch adds only a suffix. Binding only the compacted cycles is too weak; binding the current leaf exactly is too strict.
- Cycles completed by descendants while C1–C2 preparation is running need not invalidate that pending result. Applying the frozen pair still preserves C3 onward raw; the newly completed cycles simply make the next stride eligible after acknowledgement. Recomputing the “latest four” during consumption would defeat the approved descendant-tolerant behavior.
- A valid zero-reflection cycle requires the reflector to receive the complete bounded source span, not only observer output. Otherwise it cannot honestly attest that omitted source content was reviewed. The response should echo a request/cycle identity, span bounds, digest, and explicit complete/partial status; deterministic code—not prose confidence—decides coverage.
- A provider-context filter that retains the first/latest compaction summary and removes only later superseded `compactionSummary` messages is likely the minimal extension-only repair for repeated cuts. It must be active only with plastic ownership and validated with native emergency compactions, forks, and other context handlers.

### UNKNOWN / TO VERIFY

- Pi exposes no atomic “compact only if still idle” primitive. There is a race between the final idle/pending check and fire-and-forget `ctx.compact()`, whose implementation aborts an operation if one has started. A synthetic prompt-arrival race must show the settled handler/coordinator cannot interrupt a newly started response; otherwise this architecture is blocked on host support.
- The exact provider input overhead and token estimator needed to guarantee a synthetic 100k source span fits both observer and reflector requests is unresolved. It must be derived from the resolved Luna model and bounded serialization, not from either local JSON value.
- Whether filtering superseded compaction messages yields the exact intended provider context across a native emergency compaction remains to be characterized. If an earlier native summary contains facts absent from the structured ledger, custom application must fail rather than filter those facts away.

## Strategy, Decomposition, and Sequencing

Start with an inert additive contract boundary: four independently configured Luna roles, versioned cycle/attempt/compaction-state records, legacy dual-read, safety/budget primitives, and the single composition root still disabled. Session state should be reconstructable solely by folding append-only branch records. A cycle record carries stable identity, source start/end IDs, source digest, completion status, linked observation/reflection IDs, and safe boundary identity. Attempt records carry snapshot identity, outcome, retry count/cooldown, and generation so repeated `agent_start`/`turn_end` events cannot create repeated work.

The scheduler should treat 10k/20k as edge-triggered “inspect now” signals. It selects one contiguous uncovered span ending at the latest completed-turn boundary and creates at most one pipeline for its snapshot identity. No `floor(backlog/threshold)`, token slicing, polling loop, or parallel fan-out belongs in this design. Invalid, stale, timed-out, partial, or oversized results append an explicit non-complete outcome but never advance semantic coverage. Unchanged failures are suppressed after the bounded policy; source advancement or an explicit retry creates the next opportunity.

Use a single-call budget gate first. A 100k synthetic span should be scrubbed, serialized once, and either fit under the resolved model’s input allowance with output/overhead reserve or become explicit oversized/partial. Do not add multipart cycles preemptively. Only if the required 100k fixture demonstrates that safe-entry partitioning is necessary should bounded sequential parts be introduced under one cycle ID, with a hard part/call cap, per-part coverage proofs, one final reflector acknowledgement, and no full coverage until all parts verify. An atomic entry that cannot fit remains raw and relies on the emergency path.

The pure 6/4 fold should be count- and identity-based, not token-based. Only complete, current-branch, unapplied cycles qualify. It freezes the contiguous range after the previously applied cycle through the cycle before the latest four: C1–C2 at six, C3–C4 after C7–C8, then C5–C6. Structured cumulative state records compacted-through identity plus deterministic facts, active memory IDs, files/commands/errors, decisions, constraints, goals, and open loops. Luna receives that state, the exact newly eligible ledger/source evidence, and the bounded project index. Prior prose is advisory at most. Deterministic verification/repair must reject an output that cannot fit required facts within the result bound.

A staged result should be in-memory, one-slot, TTL-limited, and carry session/generation, cycle range and digest, proposed cut, prepared branch prefix vector/hash through the snapshot leaf, latest-compaction identity, structured-state digest, and invocation state. Appended descendants are accepted only as a suffix of that exact ancestor chain. A different parent chain, fork, reload, session, cut, previous compaction, missing boundary, or tool-pair shape clears it. Mark cycles applied only from a matching `session_compact` acknowledgement—not when preparation finishes, when the hook returns, or when `ctx.compact()` is called.

The settled coordinator should be event-driven: background completion and `agent_settled` are the only ordinary apply opportunities. It tracks settled generation and an apply-in-flight latch, rechecks idle/no pending messages immediately before the internal call, and passes a one-use unguessable nonce in `customInstructions`. The hook recognizes that nonce and either returns the exact revalidated staged result or cancels. Manual events without that nonce may consume a fresh valid staged result or fall through natively. Threshold/overflow may use a staged result only if it is still valid and demonstrably reduces context enough for the physical emergency; otherwise clear/invalidate it and return no result for native compaction with the visible model.

Before integrating proactive apply, prove repeated host projection. If the inferred duplicate-summary behavior is confirmed, add the minimal `context` projection needed to keep the latest cumulative compaction summary and raw preserved entries while removing superseded compaction messages. This mechanism must not become a second memory truth or general transcript rewriter. If exact filtering cannot be tied to the current branch projection, stop rather than use text heuristics.

Project storage/search can remain a separate implementation and rollback boundary after shared IDs/scrubbing exist. Canonical Markdown chunks remain human-authoritative; root/category summaries, `index.json`, the compact active-chunk index, lexical search, and architecture HTML remain derived. One shared validated assembler should produce a bounded immutable snapshot—8k summary, 4k active index, optional 4k architecture index—for `before_agent_start` and compactor input. Do not duplicate project truth into compaction prose when the per-run prompt already supplies it. Runtime wiring, the legacy project-hook bridge, and installer/settings cutover stay serialized until provider-free integration proves one owner and complete fallback.

## Risks, Routing, and Validation

The highest risks are irreversible-looking context loss from an invalid cut, interruption caused by a racy internal compact, false semantic coverage, duplicate/superseded summaries on repeated strides, stale branch consumption, and emergency fallback accidentally becoming an internal native compaction. Each has one natural control surface: cut/projector validation, settled coordinator, cycle fold, repeated-context projection, pending prefix guard, and nonce-aware hook respectively. Avoid extra queues, persistent pending blobs, timers, token-cadence schedulers, multipart fan-out, or duplicated project caches unless a required fixture proves them necessary.

Core ledger/fold and bounded local adapters fit `builder`; the host-facing compaction coordinator and custom-cut projection remain `builder` despite their consequence because they are bounded and provider-free. Routine config/docs/attribution and focused compatibility edits fit `builder-light`. Status/view presentation changes fit `builder-design`. `builder-heavy` is not justified for implementation here: live provider, reload, real migration, and multi-runtime operations are prohibited, while exceptional visual work is out of scope.

Validation must use plain Node 22.19+, Pi’s installed jiti loader, fake models, in-memory branches, and unique temporary roots only. The decisive oracles are:

- one ~100k snapshot under repeated trigger events produces one attempt/pipeline and at most one logical cycle; complete acknowledgement covers the exact span, while partial/oversized output advances nothing and does not hot-retry;
- custom-cut fixtures reject missing/non-ancestor/tool-result/orphaned-tool cuts, preserve descendants appended during preparation, invalidate same-session divergence, and prove the final provider context rather than only the appended compaction entry;
- C1–C6, then C7–C8, then another stride yield one cumulative verified summary plus exactly the latest four raw cycles, with no older compaction summary, duplicated cycle, lost descendant, fact/ID/file regression, or off-by-one application;
- background readiness during a response never calls compact; readiness after settlement applies once only with idle/no pending messages; overlapping calls, a prompt-arrival race, timeout, abort, session replacement, and stale nonce fail closed;
- internal stale apply cancels without native fallback, while real manual/threshold/overflow with no suitable pending result invokes native behavior and leaves the visible model unchanged;
- each fresh prompt and post-compaction retry receives only bounded summary + active index + optional architecture index; full chunks appear only via namespaced recall/search;
- legacy/new recall, flat fallback, migration dry-run/publication, installer staging, one-owner activation, attribution, and unrelated dirty hunks remain preserved.

Rollback boundaries should follow observable state: inert schemas/loader; pure cycle ledger and worker scheduling; host-characterized compaction preparation/projection; project context/storage; then runtime ownership and deferred bootstrap. No checkpoint should activate the new hook or retire the old project path before its fallback and repeated-compaction oracle pass.

## Open Questions / TO VERIFY

- **Repeated host projection:** prove the second and third 6/4 cuts against Pi 0.83.0’s real `buildContextEntries()` plus `context` transformation. If superseded summaries cannot be removed without losing native-only facts, stop.
- **Idle atomicity:** characterize a new prompt arriving between final checks and `ctx.compact()`. Any demonstrated visible-response abort blocks proactive application on this host.
- **Budget boundary:** resolve Luna through the runtime registry and establish conservative input/output/serialization reserves for observer, reflector, and compactor. Keep multipart support out unless the 100k oracle requires it.
- **Emergency adequacy:** define the deterministic post-apply size/retention test that allows a staged semantic cut to satisfy threshold/overflow; otherwise native fallback must win.
- **Native-summary recovery:** after a native emergency compaction, verify ledger/source branch evidence is sufficient to rebuild the next cumulative structured state without trusting or accidentally filtering the only surviving fact source.
- Live Luna quality/latency, real Windows execution, real cutover/reload, and real project migration remain intentionally unverified and must not enter implementation checkpoints.
