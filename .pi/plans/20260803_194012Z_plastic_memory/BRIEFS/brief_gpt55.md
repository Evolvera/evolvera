# Plan Brief — GPT-5.5 — cycle-based Luna compactor

## Recommendation and Goal

Regenerate the existing plastic-memory plan around a semantic cycle ledger and one asynchronous Luna compaction pipeline, rather than patching the old deterministic/Pi-cut plan. The old plan’s core assumptions are now superseded: it targets exactly three model roles and deterministic compaction (`PLAN_FULL.md:13,16`), preserves Pi’s prepared `firstKeptEntryId` (`PLAN_FULL.md:40`; `TASKS/task_05_builder.md:31`), and even leaves stale three-role/Qwen installer wording (`TASKS/task_12_builder.md:19,32`). The approved outcome instead requires four Luna roles including `compactor`, cycle-driven proactive compaction, custom cycle cuts after strict validation, and native visible-model fallback only for emergency/manual host compaction when no fresh staged result exists (`HANDOFF.md:7-16`, `HANDOFF.md:61-74`).

The simplest safe architecture is one first-party extension with a single coordinator owning: source/cycle records, bounded attempt suppression, four worker roles, Luna compactor preparation, one pending slot, idle-only apply, and project-context assembly. Keep project canonical storage/search/migration modular, but make the project read model shared by both `before_agent_start` and compactor input so long-term context is not duplicated or lost (`HANDOFF.md:45-50`). Treat tokens only as edge triggers for inspection; cycle IDs and safe turn/cut boundaries become the unit of coverage and compaction (`HANDOFF.md:18-25`).

## Strategy, Decomposition, and Sequencing

Start with an inert contract/schema/config foundation because this checkout is auto-discovered and active settings still load OM. That foundation should encode four Luna role defaults, preserve 10k/20k as edge triggers, define no ordinary token compaction cadence, add cycle/attempt/pending/compaction-state types, and keep MIT provenance. Existing `extensions/project-memory.ts` remains the bridge until the plastic runtime can provide identical bounded context.

Build the append-only session kernel around source spans and cycle state before any worker or compactor logic. A Reflector cycle closes only at a safe completed-turn boundary with stable cycle ID, start/end source IDs, ordered source-entry digest, observation/reflection links, and coverage status. The scheduler should snapshot the entire uncovered span when an edge trigger fires, compute an attempt identity from session/generation/source range/digest, and allow at most one in-flight/queued observer→reflector pipeline for the unchanged snapshot. Repeated events over a 100k delta therefore find the same attempt identity rather than creating threshold-sized repetitions. Bounded retry state should suppress unchanged failing snapshots until source advancement or explicit retry.

Introduce the project read model early enough for compactor input: canonical chunks, summaries, `index.json`, lexical search, flat fallback, and architecture index can remain modular, but context assembly should be a single validated service returning root summary (8k), compact active chunk index (4k), and optional architecture index (4k). `before_agent_start` injects only this bounded context on every visible run; `memory_recall`/`memory_search` retrieve full targeted chunks.

Adapt workers as four role-specific adapters over a shared runner. Observer and reflector may reuse OM validation patterns; compactor is a separate Luna role that consumes frozen cycle prefix plus deterministic extraction and project index; promoter remains proposal-only. No role may fall back to `ctx.model` or call `pi.setModel`.

Replace deterministic-only compaction with a cycle-aligned preparation pipeline. When the retained complete-cycle set reaches six, freeze every complete cycle before the latest four and create a compactor job bound to that prefix and the intended `firstKeptEntryId`. After C7–C8, freeze only the next eligible pair and merge with prior structured compaction state, yielding cumulative summary(C1–C4)+raw C5–C8. The compactor should never trust prior prose as sole truth; deterministic extraction and verification must own required files, commands, errors, constraints, decisions, goals, open loops, memory IDs, and cycle coverage.

Pending state is the key rollback/validation boundary. Store one scrubbed, bounded, consume-once pending result with TTL, session ID, generation, frozen entry-ID prefix fingerprint, cycle prefix, exact first-kept cut, cut type/tool-pair proof, source digest, compaction-state digest, and project-index digest. It may survive appended descendants only when the frozen prefix is still an ordered ancestor prefix and `firstKeptEntryId` still starts the latest-four raw window. Forks, reloads, session switches, branch divergence, another compaction, missing boundary, reordered prefix, or tool-result/orphan cuts clear it.

Wire runtime last, with one coordinator owning lifecycle, workers, pending, compaction hook, idle apply, and bridge predicates. Background Luna preparation may overlap visible work, but applying waits for `agent_settled`, `ctx.isIdle()`, no pending messages, and no apply lock. If preparation finishes after settlement, the same checks can apply immediately. The hook returns a staged Luna result only after revalidation; otherwise manual/threshold/overflow fall through to native visible-model compaction, while internal proactive stale-apply cancels to avoid accidental native compaction.

Counterexample to preserve for planning: a checkpoint that proves C1–C6 compaction only at exact leaf can still be invalid. If C7 appends while Luna is preparing, an exact-leaf guard would reject a safe descendant and require later rerun; worse, returning a stale/missing `firstKeptEntryId` would cause `buildContextEntries()` to keep only the compaction and descendants, dropping raw C3–C6. The validation boundary must therefore prove ordered-prefix descendant acceptance and fail-closed missing/cut rejection before any runtime apply checkpoint is considered valid.

## Risks, Routing, and Validation

Primary risks are unsafe custom cuts, internal native fallback after stale apply, false full coverage on huge/partial spans, overlapping `ctx.compact()`, and context regression after compaction retry. Mitigate by keeping one coordinator, one pending slot, one compaction hook, one project-context assembler, and synthetic host fixtures before activation. Do not split cycle schema, pending consumption, and coordinator apply in a way that lets a checkpoint import or apply without the other invariants.

Routing should stay simple: routine schemas, pure folds, project storage/search, worker fakes, and docs can be builder-light/builder where locally bounded; the high-consequence coordinator, custom-cut fixtures, installer/cutover dirty-hunk work, and final provider-free integration should route to normal builder plus independent validator. No builder-heavy route is justified because provider calls, live reload, real migration, CI waiting, and live multi-runtime operations are out of scope.

Validation must be provider-free and synthetic/temp-root only. The revised plan should retain loader smokes; pure cycle fixtures for 100k/no-loop, partial-valid output, empty-valid full-span acknowledgement, retry suppression, stale generation, six/four/stride-two folding; host custom-cut characterization; fake Luna compactor fixtures for model resolution, medium thinking, timeout/auth failure, verification/repair, scrubbing, TTL/consume once, prefix descendant acceptance, and divergence invalidation; runtime fixtures for background-ready-during-response, settled idle apply, no pending messages, single internal `ctx.compact`, native emergency/manual/threshold/overflow fallback, and no visible-model switch. Durable context oracles must prove startup, ordinary next prompt, post-compaction retry, and threshold/overflow retry all receive bounded summary + compact index + optional architecture index, never full chunks.
