# Update Evolvera PI Safely

Use this skill when the user asks to update the Evolvera checkout, application, extensions, or assets. An explicit user invocation of `/skill:self-update` requests this workflow; merely reading or loading this file internally does not. A request authorizes routine candidate preparation, inspection, validation, in-scope compatibility repairs, and activation after the required checks, while target and method remain unchanged—not destructive user-state cleanup or adoption of a different fork. Keep the previous working target active until a complete, matching candidate passes every required check. If a required proof is unavailable, do not activate; report the exact gap.

## 1. Locate and inspect the intended checkout

If a managed `pi-account-entry.mjs` exists, inspect its source inertly (never execute it) and follow its launcher file URL/path to the canonical `scripts/users/launcher.mjs`. Verify that file exists at the resolved path, derive its owning Git root, and verify that root's origin; do not trust the URL alone or accept a scratch/staged launcher. If that does not identify a verified checkout, try the existing fallbacks in order: the skill repository (`../../`), the current working directory's Git root, `~/.pi/agent`, then `~/Evolvera/Pi`. Keep this fallback order and accept only a Git worktree whose `origin` is the Evolvera repository. Verify the URL, not its directory: `https://github.com/Evolvera/Pi.git` redirects to `https://github.com/Evolvera/evolvera.git`; accept those exact GitHub HTTPS or SSH identities, not a lookalike host. Report which verified checkout and branch are involved. If no existing checkout is verified and `~/Evolvera/Pi` does not exist, it may be cloned from the verified official Evolvera URL using existing scoped GitHub authentication, then verify its origin. Never overwrite, repurpose, or clone into an existing path; if the clone destination exists, stop without touching it.

Inspect status, current branch, upstream, origin, local commits, and the full dirty diff before proposing changes. Preserve branch, upstream, local commits, and all dirty/untracked work. Never reset, stash, clean, force-pull, discard, or resolve a conflict by choosing a side. Fetch/inspect the configured upstream and prepare a candidate that retains local commits; only use a fast-forward-compatible update. If branch intent, remote, divergence, conflict, or dirty-work impact is unclear, stop without changing the checkout.

## 2. Select and reconcile a candidate

Select an official Evolvera source revision and SDK version; do not downgrade. Inspect release/source identity rather than trusting a release-service payload or package name blindly; reject an unexpected package/fork. If an official candidate SDK version is not yet supported by repository pins, stage it as code only and adapt the repository's pins, transforms, and patch compatibility on the working branch before activation. Never relabel unsupported pins or activate an untested version. Do not assume the default branch, a floating `latest`, or a release payload is the intended target.

Reconcile the whole update before activation: repository app changes, SDK pins and dependency metadata, SDK transforms/patch chain, package patches, extensions, and shipped assets. Follow the repository's authoritative version/patch definitions and update all of them as one compatible candidate. Do not silently relax unsupported patch anchors or omit a component because it is inconvenient. No extra approval is needed for ordinary in-scope candidate compatibility repairs. If the selected official revision has no app update, state that and do not invent one.

## 3. Prepare in isolated candidate resources

Prepare the checkout, application, package/extension updates, and assets in scratch candidate locations; do not alter the active checkout, SDK, entrypoint, or installed resources during preparation. Before any command that may write, resolve its executable, arguments, environment precedence, config files, hooks, setup/teardown, network behavior, and every reachable resource. Prove each target is either absent (`NO_STATEFUL_RESOURCES`) or uniquely run-owned and disposable (`DISPOSABLE_VERIFIED`), including the package prefix, SDK root, cache, user/global config, HOME, and actual active command/entry source. A temporary HOME, `.env.test`, prefix label, or isolated-looking path alone is not proof. If exact target ownership cannot be demonstrated, do not run the command and do not fall back to the live installation.

The supported SDK CLI has distinct effects: `pi update` updates the application; `pi update --extensions` updates packages only; `pi update --all` does both. It has no real preview/check, dry-run, or target-version option. A test fake accepting `--check` does not establish native preview support. Native self-update derives its install package/version from the release service and can uninstall the currently installed package if that package name changes. Therefore use `pi update` only in proven isolated resources and only when its resolved official package identity/version is exactly the reviewed candidate; never follow a changed/unexpected release payload. Use `--extensions` only in the proven isolated candidate for the reviewed package update. Do not treat either command as packages-only when using `--all`, and never use live `pi update`, `--all`, or an installer as a fallback. If actual write effects or release target cannot be controlled and verified, preserve the old target and report why staging is unavailable.

Prove the first write's actual effects on an isolated candidate before batching further package or asset updates. Keep recovery material independent of the target being changed. Clean up only failed scratch resources owned by this run; retain a bounded set of last-known-good or still-in-use SDKs with a named retention reason and cleanup trigger. Never eagerly delete an SDK directory that an existing process might still use.

## 4. Validate the complete candidate before activation

Inspect the candidate diff and source/pin metadata, then run focused tests for each changed concern and supported repository validation. Exercise the candidate's own synthetic account bootstrap, managed entrypoint, and extension/streaming paths where affected; do not use real credentials, sessions, or user data as fixtures. Repair stale in-repository extensions, pins, and patch anchors on the candidate branch before publishing; do not broaden unsupported anchors just to make a patch pass. No extra approval is needed between routine inspections, tests, and in-scope candidate repairs.

Check the candidate SDK's declared Node engine and satisfy its minimum; also confirm the intended installer baseline of Node.js 22.19.0 or newer. Do not use environment overrides to bypass the requirement. Do not use VS Code's **Upgrade Pi and Packages** action in `pi-vscode` 0.0.9: it hardcodes `@mariozechner/pi-coding-agent` and may replace the required `@earendil-works/pi-coding-agent` fork.

For managed entrypoints, inspect the actual resolved command, generated descriptors, symlink/shim referents, and native SDK source before activation. Use the documented entrypoint-preparation CLI in `docs/auth-only-accounts.md` (`scripts/users/entrypoints.mjs`) to validate the candidate SDK, including dependency metadata and source pins. When rendering, pass `--launcher-path` explicitly as the final canonical repository `scripts/users/launcher.mjs` path; never rely on the renderer's default path from a scratch/staged copy. Preserve canonical target paths and existing command identity; do not point a managed entry at scratch paths. A direct SDK invocation or `pi --version` alone does not prove the managed entry, account selection, or startup artwork works. Validate SDK compatibility before rendering/activating the entry, then verify the resulting invocation plus synthetic account selection and artwork. Preserve auth, registry, sessions, credentials, settings, extensions, custom data, native CLI routing, and active processes.

Publish the repository candidate to the intended branch only as a fast-forward that preserves its local commits and working tree; if that cannot be done safely, leave the checkout unchanged. Activate only a fully validated candidate whose repository, SDK, patches, packages, assets, and managed entry all match. Do not replace an SDK package directory used by a running process, or automatically `/reload` changed SDK code into a process that may hold old modules. Use a fresh invocation to verify startup, command routing, account selection, and artwork—not just a version string. Keep the previous working target available until verification succeeds.

## 5. Recovery, reporting, and stop rules

If required proof or focused validation is missing or fails, leave the prior working target active and report the exact gap; do not improvise a live fallback. Roll back only code or entrypoint changes declared for this candidate, from an independent recovery artifact and through a supported method. Never automatically roll back user state. An unexpected shared/live mutation or ambiguous effect is an incident: freeze all writes, perform read-only diagnosis, and request fresh authorization before any recovery or cleanup.

Report the verified checkout, branch/upstream, candidate revision and SDK version, components changed, validations and results, activation status, and any retained SDKs with their reason/cleanup trigger. Do not expose secrets, session data, or unrelated local changes. Separate source-update success from candidate validation and activation success.
