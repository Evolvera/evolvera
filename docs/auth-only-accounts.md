# Auth-only accounts

The managed launcher keeps Pi's native CLI as the sole owner of argument parsing, session selection, project trust, settings, resource loading, and interactive/RPC/print dispatch. It prepares an exact-version source bridge in a fresh temporary code stage; it does not patch or install the SDK. Managed SDK 1.2.0 startup skips the installed SDK's Windows quarantine cleanup: starting an account session must not delete artifacts owned by earlier processes. Native early commands keep their stock SDK behavior; this bridge does not execute updates automatically.

## Account and session behavior

- Start directly in a saved account with the managed launcher's leading `-u <id>` or `--user <id>` selector (also `--user=<id>`): for example, `pi -u evolvera -c` or `pi --user evolvera --session <session>`. Place the selector before native options and messages. Prefix parsing stops at the first other argument, so later native arguments—including literal `-u`/`--user` values and everything after `--`—are passed to Pi unchanged. A syntactically valid selector binds the ordinary version-1 account launch context; it does not create another account-selection namespace. Same-ID inherited context is accepted, a different-ID selector fails with `ACCOUNT_BINDING_CONFLICT`, and existing multiple-context-source rejection remains. Invalid, empty, missing, or repeated leading selectors fail closed before native SDK dispatch. Help/version and native update/package/config dispatch remain inert; the selector is stripped before forwarding native argv.
- On a fresh interactive application session without an explicit selector, select a saved account with Up/Down and Enter before an account credential store or model runtime is constructed. The menu includes `Create new account`; only creation asks for `create <id> [label]`. Escape/Ctrl-C cancels. Headless invocations still require an explicit selection, and inherited/bound accounts bypass the menu. Existing sessions use their stored `pi.account` custom entry; a legacy session is associated once. New/fork session replacements inherit only from the native predecessor. Unknown, malformed, or conflicting bindings fail closed.
- The first application account is immutable for that launcher invocation. A session bound to a different account needs a fresh process. The launcher will not replace, signal, spawn, or rewrite the environment of another process to change accounts.
- Fresh invocations of the managed native launcher may inherit only a versioned, non-secret launch context (`accountId` and absolute shared `registryPath`) in `PI_ACCOUNT_LAUNCH_CONTEXT` or its wrapper-owned `--usuario-context` flag. It contains no credentials or session/config payload. An inherited account selects fresh/unbound sessions without prompting; a conflicting native `pi.account` binding fails before account-store construction. Independent roots without that context still use the account picker. The native `pi.account` session binding remains authoritative.
- Account-context propagation and entrypoint preparation have bounded synthetic coverage. Publishing the rendered commands is a separate, explicitly authorized local activation; rendering alone never proves an installed command was activated. Orca's app/controller does not necessarily inherit the PI parent environment. The explicit child-command bridge uses documented `terminal create --command` (and `--shell` on Windows), not an undocumented environment/RPC override. The public Orca CLI 1.4.217 guide exposes no per-launch environment flag for worktree `--agent`; automatic GUI/`--agent` inheritance and DEV runtime support remain unverified. No worktree/account state or global current-account file is introduced.
- `/usuario status`, `/usuario list`, and `/usuario create <id> [label]` remain available. `/usuario use <id>` validates the account and gives fresh-process guidance; it does not switch or restart the current session. Creating an account creates only its credential namespace, not credentials or history. `/usuario remove <id>` requires an interactive confirmation naming the account and explaining that credentials and history remain on disk; sessions bound to it cannot resume until its registration is restored. The fixed account for the current process cannot be removed, and headless/no-confirmation contexts fail closed. Removal deletes only the registration and first writes a fresh recovery copy of that registry record adjacent to the registry. This is metadata for possible manual recovery; there is no built-in restore command, and profile, credential, and session files are never removed.
- Account credentials live in the registry-issued account namespace. Pi's normal agent directory, shared `models.json`, cwd, settings, sessions, history, memory, agents, skills, plugins, and other resources remain shared. SDK 1.2.0's personalized OpenRouter catalog entry in the native `models-store.json` is namespaced by canonical registry identity and selected account ID; the native file/store remains authoritative and no parallel store or catalog projection is created. Anonymous metadata cannot read, write, or delete an account's personalized entry.
- SDK auth resolution receives a sealed account context. Catalog auth-bearing fields are filtered according to the selected-account policy; explicitly supported owner literals remain by reference. Only the registry-issued `evolvera` profile with `adoption: reference` receives a frozen factory-time process-environment snapshot, preserving its existing environment-backed credentials without moving them. Metadata, new accounts, and other account IDs receive an empty environment. Shell-auth execution and filesystem credential fallback remain disabled; this does not certify opaque provider/extension auth. Native provider/model algorithms and shared model definitions remain native.
- Metadata/help/version and other early no-auth paths stay lazy and do not prompt. Native `pi update`, `pi package`, and `pi config` dispatch directly to the installed SDK without account selection or SDK staging. Auth utilities select an account explicitly before constructing credentials. Metadata uses inert credentials and no persistent account store.

## Local activation without installers

For an explicitly authorized activation, validate the target SDK package with the entrypoint preparation CLI, then publish the resulting bootstrap and command descriptors to the already-resolved command directory. Preserve the original shims independently; do not run either installer, modify PATH, patch SDK files, or restart existing processes. The CLI verifies supported SDK source and dependency pins before emitting descriptors; if validation fails, do not publish or repoint the managed entry. All published commands use the same `launcher.mjs`; recovery artifacts are retained, not configured as a second live entry.

Register the existing account as `id: evolvera`, `label: EVOLVERA`, `agentDir: <existing native agent directory>`, `adoptExisting: true` through `registerUser`. This adopts the credential namespace by reference: do not copy, move, delete, rewrite, or reauthenticate `auth.json`. Preserve existing registry records. The normal account picker still applies to fresh independent sessions; choose **EVOLVERA** to use the existing namespace. Publishing `pi` does not add automatic GUI/IDE account inheritance.

Before activation, validate the same generated bootstrap in a newly owned synthetic profile. After publication, exercise the actual command under that isolated profile and verify `/usuario status` and `/clean-ui status`; never use the real credential namespace as a test fixture. A synthetic PASS proves the command route, not real provider authentication. Npm/SDK updates may regenerate command shims, so verify the account entry after an update rather than assuming it survived.

Do not replace a different SDK version in a package directory still used by running PI processes. A 0.83.0 process can retain the old `pi-ai` text/auth modules while lazily importing new 1.2.0 modules from the same paths: the old text module lacks `getSystemMessageText`, and the old OAuth resolver calls `refresh` without the signal required by the new Anthropic provider. Reauthentication does not clear that module cache, and `/reload` is not an SDK process restart. If such a replacement has already happened, the operator must close the old process and start a fresh `pi`; do not reset credentials or fabricate missing exports. Existing processes must not be automatically terminated by activation.

The managed launcher's default temporary parent resolves `os.tmpdir()` to its canonical path before allocating a fresh SDK stage. This handles macOS `/var` → `/private/var` aliases without weakening the stage's strict source/import/path checks. Native startup validation must include an aliased temporary directory, not only an already-canonical synthetic `TMPDIR`.

## Inert entrypoint preparation — not activation

`install.ps1 -PrepareUsuarioEntry -UsuarioBinDir <absolute-bin-directory> -UsuarioSdkRoot <absolute-sdk-root> [-UsuarioNodePath <absolute-node-executable>]` returns JSON artifact descriptors and exits BEFORE normal installer operations. `install.sh --prepare-usuario-entry --bin-dir <absolute-bin-directory> --sdk-root <absolute-sdk-root> --platform posix [--node-path <absolute-node-executable>]` does the same. Both invoke the entrypoint CLI, which validates the supported SDK package metadata, dependency metadata, and pinned source hashes before emitting descriptors. Validation is read-only: neither preparation mode writes the described files, imports the SDK, installs packages, changes PATH, or replaces existing commands. Unsupported or modified SDKs are rejected before descriptor output. The ordinary installers now default to the pinned 1.4.0 runtime and its required patches; 1.3.0 remains supported. Normal installation is NOT the activation procedure for this managed SDK 1.0.1/1.1.0/1.2.0/1.3.0/1.4.0 feature. Exact pinned sources and dependencies for these versions are supported; unknown or modified SDK sources fail closed before staging or entrypoint descriptor publication.

`scripts/users/entrypoints.mjs` renders one `pi-account-entry.mjs` bootstrap plus the platform command sources. Every command points to that bootstrap, which calls the existing `launchUser(argv, {packageRoot})` with explicit SDK and launcher paths. The managed launcher remains the sole account-startup authority; native PI still owns CLI/session/resource dispatch. There is no original-SDK fallback entry. Native argv, stdin and exit behavior have fake-launcher shell coverage in cmd.exe, Windows PowerShell and Git Bash. The generated POSIX entry is also exercised against SDK 1.4.0 with a selected synthetic account and an in-process faux provider; this proves the command route, not real provider authentication.

`scripts/users/child-command.mjs` exports the pure renderers `buildAccountChildCommand` and `createOrcaChildLaunch`, plus the explicit `launchOrcaAccountChild` caller. Call it only from the managed parent process that already publishes `PI_ACCOUNT_LAUNCH_CONTEXT`; it fails closed when that exact context is absent or malformed. Supply the absolute Orca executable, Node executable, and bootstrap entrypoint paths from the actual rendered entry artifact, along with the explicit shell and worktree selector:

```js
import { launchOrcaAccountChild } from "./scripts/users/child-command.mjs";

const status = launchOrcaAccountChild({
  orcaCommand: ORCA_ABSOLUTE_EXECUTABLE,
  nodePath: RENDERED_NODE_EXECUTABLE,
  entrypointPath: RENDERED_ACCOUNT_ENTRYPOINT,
  shell: "powershell.exe", // use an explicitly selected supported shell
  worktree: EXACT_WORKTREE_SELECTOR,
  argv: ["--", "literal", "native", "arguments"],
});
```

The caller invokes the supplied Orca executable exactly once with `shell: false`; the child receives the rendered `--usuario-context` argument while its copied environment omits the parent context marker. It does not infer paths, account, controller, or worktree from cwd, PATH, GUI, or global state, and does not install, retry, or configure a GUI. The module CLI likewise requires `--orca-command`, `--node-path`, `--entrypoint-path`, `--shell`, and `--worktree`; repeat `--arg <literal>` to pass native arguments. It intentionally has no context override and therefore requires the published parent environment. The pure renderers remain non-actuating. The context argument precedes native argv; literal arguments after `--` remain literal. Only the new terminal shell's inherited context is cleared, with PowerShell restoring it afterward; cmd command text targets a new terminal shell and rejects percent, bang, double quotes, and control characters. Windows context/path transport to WSL is not inferred.

The managed Windows command `/usuario orca <worktree-selector>` calls this same bridge from the fixed-account parent, using the running bootstrap, Node executable, PowerShell and Orca's public `%LOCALAPPDATA%/Programs/orca/resources/bin/orca.EXE` location. It validates the root session and published account context, launches at most once, and returns a bounded error on failure. It does not modify Orca's managed status/prefill/spinner extensions, create worktrees, or add automatic GUI inheritance.

This is a bounded explicit process caller, not automatic GUI/controller inheritance. The isolated source suite uses an injected fake spawn only; no actual Orca process, live worktree, native app, SDK, or GUI/IDE/DEV path was exercised. Automatic GUI/IDE/DEV inheritance remains NOT VERIFIED. The earlier explicit caller has a limited human-reported child `principal` status result; the newly added `/usuario orca` command has synthetic coverage, not a new live-terminal certification. Existing bootstrap/source and historical evidence remain as described in `.pi/build/auth-only-entry-inheritance-verified.md`; no live Orca terminal or worktree was touched.

## Scope and limitations

This boundary isolates the SDK's credential store, auth context, and supported model configuration; it is not an OS security boundary. Native Windows/TTY presentation, full provider execution, downstream AWS/GCP credential behavior, and opaque extension-specific auth are **UNVERIFIED**. Synthetic source-extracted/fake-SDK tests do not certify installed SDK execution, native CLI behavior, provider/network behavior, or Plastic/subagent runtime behavior. The SDK's public completion method is checked with fake parent references; no production adapter is added. SDK 1.2.0 support preserves its native schema validation and OpenRouter personalization while scoping only that personalized cache key to the selected account; shared `models.json` and all non-personalized provider cache keys remain native/shared. This compatibility checkpoint does not certify native TTY/provider journeys. Existing Plastic SDK-compatibility changes remain protected, separate, uncommitted WIP: they are not included or certified by this account checkpoint. A clean checkout must not be treated as having those changes.

The earlier full-profile workspace/session/environment admission and same-terminal replacement supervisor are historical evidence, not active account startup paths. Account-state migration is not part of this feature. Local entrypoint activation is a separately authorized publication, with no credential migration or existing-process restart.
